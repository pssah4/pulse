# Commands

## Slash commands

Type `/pulse` in Claude Code, in the terminal or the IDE; autocomplete lists the rest. In Codex, type `$pulse:pulse`, in the CLI and the IDE extension alike; the Codex CLI also lists the skills under `/skills` > **List skills**, or as soon as you type `$`, by the names `pulse-ba (pulse)` and so on, the IDE extension under **Skills** when you type `/` in the prompt box. Support for GitHub Copilot will follow. Each command is its own skill and can be called on its own; in the Pulse flow they hand over to each other without asking and stop only [where a person decides](../concepts/v-model#where-pulse-stops-for-you). `/pulse-build` builds one item in your session, `pulse go` runs the same build for every ready item in parallel, in your own terminal.

Codex also lists `pulse:pulse-plan`, a step that other commands run on their own. `/pulse-re` plans each feature, improvement, or fix you approve in its session (an epic gets no PLAN), `/pulse-build` and `pulse go` plan an approved item that has no PLAN yet, and both run the review and the audit. Claude Code hides it from its menu, Codex does not. See [Planning](../guides/pulse-plan).

## The pulse command line

Every deterministic step is a script, so no model has to do bookkeeping. The Pulse hooks tell the agent where the CLI lives. For your own terminal, `pulse setup --cli` puts the `pulse` command in `~/.local/bin`, once per machine ([Installation](../tutorials/installation)); `/pulse` offers the same where Pulse is not set up yet. Python 3.9 or newer, standard library only.

Reads come from a local cache (`--fresh` skips it); `--json` gives machine-readable output. Exit codes: 0 done, 1 refused, 2 cannot act here (no repository, ambiguous remotes, `gh` failed, a spec for `pulse new --spec` that is missing or not on origin, `pulse number --apply` or `pulse new --spec` while origin did not answer or a ref they need is not as origin has it).

## pulse auto

Each person switches their own auto mode, per gate and never for all three at once: `pulse auto plan on` (gate 1, specs get planned), `pulse auto build on` (gate 2, plans get built), `pulse auto merge on --for 8h` (gate 3, green pull requests get merged, until a time), and `pulse auto merge off`. `on` first says what then happens without asking you, for which items, and as which GitHub login, and asks once; `off` asks nothing. A switch acts only in your own `pulse go`, and only on items you opened or claims you hold; other people's switches never act for you. `pulse auto` alone shows yours and everyone else's, with since and until. Only a person switches, in their own terminal or with `1` `2` `3` in the [live map](../guides/pulse-map#auto-mode): with an agent marker in the environment or without a terminal, `on` and `off` refuse, and the [Pulse guard](../concepts/parallel-work#levers-belong-to-a-person) denies them to agents.

The switches live in the issue "Pulse auto mode" (label `pulse:auto`), which the first `on` creates and pins where one of the three pin slots is free. Each switch is a comment with the line `<!-- pulse:auto gate=<gate> state=on|off until=<time>|- -->`; per login and gate the newest comment counts, and its GitHub author is the one who set it. The issue text is an overview only. A switch past its time is off without anyone writing, and a gate is off for good for a login once one of its toggle comments was edited, whoever edited it. With two open issues that carry `pulse:auto`, every switch is off for everyone until one is closed, and the map and `pulse status` say `auto off: two auto issues #<a> #<b>, close one`. `pulse status --json` carries them as `auto`, per login and gate.

## pulse check

| Rule | Checks |
|---|---|
| C1 | relative Markdown links in `_devprocess/` and agent guides resolve; a Markdown file there that is a symlink, a FIFO, or a device is named and never read |
| C2 | backticked repository paths in agent guides (AGENTS.md, CLAUDE.md, the system map, the decisions router) exist |
| C3 | no code paths in the core sections of a decision record |
| C4 | no work state (`status`, `phase`, `claim`, ...) in any `_devprocess` frontmatter |
| C5 | artifacts stay within their line cap plus 10% (an epic's `## Items` list does not count), unless they state a reasoned exception (`## Reasoned exception`, the heading in any case) |
| C6 | every feature spec has an Activation Path with Type and Identifier |
| C7 | every `FIXME(stub):` in the code names an item, an open one when the cache knows |
| C9 | every spec's `parent:` and its epic's `## Items` list agree |
| C10 | every spec's file name starts with the ID its place in the tree calls for (`EPIC-04`, `FEAT-04-02`, `FIX-04-02-01`); `pulse number --apply` fixes what it reports |
| R1 to R6 | an approved item's spec is one an agent can plan from, read from the base branch (see [/pulse-re](../guides/pulse-re#quality-gates)) |

Files under `_devprocess/temp/` are not checked: temporary test files live there only until they are deleted.
