# Commands

## Slash commands

Type `/pulse` in Claude Code, in the terminal or the IDE; autocomplete lists the rest. In Codex, type `$pulse:pulse`, in the CLI and the IDE extension alike; the Codex CLI also lists the skills under `/skills` > **List skills**, or as soon as you type `$`, by the names `pulse-ba (pulse)` and so on, the IDE extension under **Skills** when you type `/` in the prompt box. Support for GitHub Copilot will follow. Each command is its own skill and can be called on its own; in the Pulse flow they hand over to each other without asking and stop only [where a person decides](../concepts/v-model#where-pulse-stops-for-you). `/pulse-build` builds one item in your session, `pulse go` runs the same build for every ready item in parallel, started in your own terminal or with `/pulse-go`.

Codex also lists `pulse:pulse-plan`, a step that other commands run on their own. `/pulse-re` plans each ready feature, improvement or fix in its session (an epic gets no implementation Plan). `/pulse-build` and `pulse go` reuse an existing Plan or prepare one for a valid published spec, then run review and audit after the build. Claude Code hides it from its menu, Codex does not. See [Planning](../guides/pulse-plan).

## The pulse command line

Every deterministic step is a script, so no model has to do bookkeeping. The Pulse hooks tell the agent where the CLI lives. For your own terminal, `pulse setup --cli` puts the `pulse` command in `~/.local/bin`, once per machine ([Installation](../tutorials/installation)); `/pulse` offers the same where Pulse is not set up yet. Python 3.9 or newer, standard library only.

Run `pulse` without arguments for the current state and possible next steps, once. It starts no runner or live Map. Outside a configured project, it explains how to get started.

In `pulse map`, the bottom row shows `? help`. Press `?` for navigation, the workflow and every CLI command with its purpose, context and example. Scroll with the arrow keys or `j`/`k`, page with PgUp/PgDn, and return with Esc or `q`. The help adapts to the terminal width; Enter and action keys execute nothing while it is open.

The workflow is spec, published Plan, RED tests and test freeze, build and checks, review and audit, then integration. `pulse go` follows that process for queue work and an optional saved goal. Regular checked results complete automatically by default; an explicit manual policy waits for personal approval. Hooks, holds, current rights and exact result/base bindings still apply. Removal always requires separate personal confirmation.

Reads come from a local cache (`--fresh` skips it); `--json` gives machine-readable output. Exit codes: 0 done, 1 refused, 2 cannot act here (no repository, ambiguous remotes, `gh` failed, a spec for `pulse new --spec` that is missing or not on origin, `pulse number --apply` or `pulse new --spec` while origin did not answer or a ref they need is not as origin has it).

## pulse auto

Regular checked results complete automatically by default. `pulse auto` shows the repository policy. A person with repository write access can choose manual final approval with `pulse auto merge off`, or restore automatic approval with `pulse auto merge on`. `--for 8h` limits an explicit automatic setting to eight hours; expiration requires manual approval. The [Map](../guides/pulse-map#auto-mode) exposes the same setting with `3`.

Policy changes are saved locally and synchronized in the background. A pending local off blocks automatic integration immediately. Confirmed changes apply to the repository; existing manual settings remain in force. Every integration still requires current checks, exact result and base versions, and current authority. Holds, revoked results and destructive removal keep their separate boundaries. Historical auto comments grant no authority.

## pulse check

| Rule | Checks |
|---|---|
| C1 | relative Markdown links in `_devprocess/` and agent guides resolve; a Markdown file there that is a symlink, a FIFO, or a device is named and never read |
| C2 | backticked repository paths in agent guides (AGENTS.md, CLAUDE.md, the system map, the decisions router) exist |
| C3 | no code paths in the core sections of a decision record |
| C4 | no work state (`status`, `phase`, `claim`, ...) in any `_devprocess` frontmatter |
| C5 | artifacts stay within their line cap plus 10% (an epic's `## Items` list does not count), unless they state a reasoned exception (`## Reasoned exception`, the heading in any case) |
| C6 | every feature spec has an Activation Path with Type and Identifier |
| C7 | every `FIXME(stub):` in the code names an item, an open one when the cache knows |
| C9 | every spec's `parent:` and its epic's `## Items` list agree |
| C10 | every spec's file name starts with the ID its place in the tree calls for (`EPIC-04`, `FEAT-04-02`, `FIX-04-02-01`); `pulse number --apply` fixes what it reports |
| R1 to R6 | a published spec is one an agent can plan from, read from its item branch or the base branch (see [/pulse-re](../guides/pulse-re#quality-gates)) |

Files under `_devprocess/temp/` are not checked: temporary test files live there only until they are deleted.
