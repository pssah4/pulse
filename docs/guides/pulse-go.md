# pulse go

`pulse go` is a script that plans and builds everything that can run, in parallel, until the ramp is empty. Start it in your terminal, or explicitly ask `/pulse` (in Codex `$pulse:pulse`) to start it from your interactive chat. The skill executes the existing runner in a foreground TTY. The model does not decide how much runs at once, so it cannot forget to parallelize. The rules behind the decision are on [Parallel work](../concepts/parallel-work).

[`/pulse-build`](./pulse-build) is how one item gets built; `pulse go` starts that same discipline for every ready item at once, one headless agent per item in its own worktree, checks itself that the spec tests failed before the code, and runs three gates after each build: tests, review, and security audit. Nobody hands items over by hand: what the ramp has released, `pulse go` picks up in ramp order.

Spec approval for planning is automatic by default; implementation waits for manual PLAN approval. You review the completed PLAN before the build starts. Explicit auto settings and their expiry remain authoritative. Claude Code and Codex follow the same flow.

## Before the first run

`pulse go` needs `verify` and `[spec_tests]` in `.pulse/config.toml` on the base branch as origin has it: `verify` runs the project's tests on the completed result in the tests gate, and `[spec_tests]` names the runner of each spec test file ([Configuration](../reference/configuration)). Without either, or when the base branch cannot be fetched at the start, `pulse go` claims nothing and exits with 2 (`pulse setup --verify "<cmd>"` sets it; commit and push the file). With `setup` there too (`npm ci`, say), every worktree of the run is set up before its agent starts.

It also checks the agents of the run before it claims anything. An agent that is not installed (neither on `PATH` nor bundled in a VS Code extension of Claude Code or Codex) claims nothing in this run, and the start says so. When no agent is left to build, the run does not start.

## Start a run

```bash
pulse go
```

`pulse go` runs in the foreground of its terminal or the interactive skill's persistent PTY. No [live map](./pulse-map#it-starts-nothing) or hook starts it automatically, and it opens no window. Its first line names `cap` and the agents, its output stays in that terminal, and Ctrl-C stops it (see [One run per clone](#one-run-per-clone)). In a chat you can ask the skill to stop its retained process session. `cap` in `.pulse/config.toml` limits how many agents run at once, in every phase and across all agents; `agent` there names the agents (see [Two agents at once](#two-agents-at-once)), and no flag changes either for one run. `pulse status` shows beforehand what the next run takes: the rows of the ramp that start next, and the approved items that need a plan. An explicit skill start keeps the session markers and changes no approvals or auto switches. Runner agents, child sessions, and starts without a TTY are refused before project access.

## What a run does

1. **Reads the ramp**: ready items in one order, files disjoint from running work, up to the free slots. The order puts no item before an open blocker; among the rest it goes by effective priority, the best `P0` to `P2` label of the item and of everything it unblocks (an item without one comes after `P2`), then by number. So a `P2` item that blocks a `P0` item comes before a `P1` item. Before each round it fetches from origin, at most every 30 seconds, so it sees the PLANs and branches other clones pushed. A merge at gate 3 comes first, then planning jobs and builds in that one order. An approval counts only from someone who may push to the repository: before it claims an item, `pulse go` asks GitHub who added `pulse:approved` (gate 1) and, for a build, who wrote the comment `plan ok at` with the blobs of the item's `Plan-ok` line (gate 2), once per login and run; an approval of anyone else is named in the report and the item waits.
2. **Merges the docs PR of an approved item** whose spec is not on the base branch yet (gate 1, "spec in PR #m: pulse go merges it" in the ramp). It merges only when git's merge of the PR into the base changes nothing outside `_devprocess/` and carries the spec, every spec in it passes R1 to R6 at its head, and, after `pulse go` set the status `pulse/tests` ("docs only: R1-R6") there, the whole check rollup of that head passed; the merge is bound to that head. That head and the spec path are the ones a person approved: the comment `gate 1 ok at <head> <spec path>` from someone who may push names them. A PR pushed to since stands as `docs PR changed since approval` until someone approves it again. Otherwise the report says why, and a later run tries again. A spec neither on the base branch nor in an open pull request stands as `spec not on <base>`, and nothing plans it.
3. **Plans an item or repairs its unapproved PLAN.** An approved item with a ready spec and a missing or structurally invalid PLAN takes a free slot for planning, even while its blockers are open. A repair edits the existing PLAN at the same path and preserves its risks. A PLAN with any previous approval waits for a person before it is rewritten. The planner runs `pulse check --plan <path>` before publication: all P1 to P6 findings together, offline, without a test suite. A PLAN that still fails goes back with the findings, for up to two fix rounds; after that the item stops with all findings and a next action. A valid PLAN waits for manual approval before the build. `pulse approve <n>`, or `a` in the map, binds the pushed PLAN and approved spec blobs. An explicit `pulse auto build on` may delegate this decision; expired delegation, `risk:` in the spec or PLAN, open prerequisites and failed checks still hold the build. A PLAN or spec changed since personal approval waits again. With explicit build delegation, a valid PLAN is built in the next round on the same claim when the ramp lets it. Before the push, each entry under `needs:` becomes a blocker of the item: `#m`, or the title of an open draft, as it is; a new title becomes a draft item with the item's type and parent, at most one new draft per round, and `#m` takes the title's place in the PLAN. An entry that would close a cycle becomes no edge and goes back to the planner as a finding. The planning prompt names the open drafts that came from `needs:`, so a second planner that needs the same work reuses its draft.
4. **Claims each item** for this run: it assigns you on the board and puts the run's mark on the item, with the files of the item's PLAN, so every clone's ramp keeps other items off them. Of two concurrent claims the older mark wins, also while the other person's assignee does not show yet: a claim that finds a fresh mark of someone not yet assigned before its own waits a moment and reads again. Should both claims still win, the check before each push below settles it. No other session of yours can take the item meanwhile. A claim lost this round is tried again in the next. An interactive session whose claim lost to an older one learns it from its next `pulse claim` or `pulse release`, which names who holds it now.
5. **Creates a worktree** in the repository, `.worktrees/<n>-<slug>`, on the item's branch, so a container that mounts only the project folder sees it. Git ignores the folder through `.git/info/exclude`, and `pulse check` skips it; test runners that search dot folders (vitest, jest, ESLint) need `.worktrees/` in their ignore list, while pytest and TypeScript skip it on their own. Claude Code reads `CLAUDE.md` files from its working directory upward, so its sessions in `.worktrees/` also read the main checkout's `CLAUDE.md` and `CLAUDE.local.md`. A worktree an older Pulse made beside the repository, `<repo>-<n>-<slug>`, is used where it lies; a branch checked out in any other worktree (one you made, `.claude/worktrees/`) is never built there, and the item fails with git's message. An item that already has a branch, here or pushed from any clone, keeps it; a new one gets `<type>/<n>-<slug>`, started from the base branch as origin has it. A branch pushed from elsewhere is caught up first. Then `pulse go` runs `setup` in the worktree, outside the agent's sandbox, and again whenever a lockfile in it changed; a setup that fails there fails the item with `pulse:failed`. Before a build, the branch merges in the base at the commit the run checked: a conflict fails the item and names the files and the worktree to resolve them in, and a project hook that refuses the merge commit pauses the run.
6. **Starts one headless agent per item** with the build instructions, the PLAN, and the spec. The agent writes the spec tests of the PLAN's first wave first (one per requirement), runs them once, and commits them alone as `test: spec tests for #<n>`; from then on they are frozen. Then it works through the PLAN's tasks test-first, runs targeted checks and additional PLAN checks that `verify` does not cover, commits, and touches nothing on GitHub. The supervisor owns the full `verify` on the completed result, so its build agent does not repeat that suite. Work it finds that has to be built first goes under `needs:` in `_devprocess/plans/<n>-needs.md`; `pulse go` makes it drafts and blockers as for a PLAN, and the item waits for them.
7. **Checks RED and runs the gates.** `pulse go` checks out the commit that froze the spec tests in the item's own worktree, where `setup` ran, runs the runner of each frozen spec test there, and goes back to the branch: before the code exists, every runner must fail. Without that commit the tests gate is red. Then the three gates run in order: `tests` (`verify`, the runner of each frozen spec test, and `pulse check` on the files the branch changed; the spec tests must be as they were frozen), then `review` and `audit` in one fresh session (scope branch against the base, [/pulse-audit](./pulse-audit)), each with its own report and verdict, also for an item whose spec or PLAN has `risk: [security]`. The session runs in a gate directory beside the worktree, `.worktrees/<n>-<slug>.gate`, an empty git repository (Codex starts only inside one). Its `session/` folder is the session's working directory: a fresh checkout of the worktree's last commit, which `pulse go` pushed, in `session/tree/`, and the report next to it. The session runs git on that checkout as `git -C tree diff`, `log`, `show`, or `status`, the four forms the allow list of a Claude session adds for it, since a headless Claude refuses `cd tree && git ...` in one command. Nothing uncommitted or ignored in the worktree reaches the session, and the branch's `.claude/` and `AGENTS.md` are not its project; a change to them shows in the brief. A session that changes the worktree or its branch gives no verdict. `pulse go` removes the gate directory before each session and once its verdict is read, after a timeout, an error, or a stop too. Runners run one at a time per machine, under `~/.cache/pulse/spec-tests.lock`, with `CI=1`. Each gate leaves its result as the commit status `pulse/tests`, `pulse/review`, or `pulse/audit` on the head it judged and in `~/.cache/pulse/<clone>/gates/<sha>`, outside the git directory a Codex agent can write ([what `pulse go` keeps there](../reference/configuration#what-pulse-go-keeps-outside-the-git-directory)). A review or audit counts as green only when its first line reads exactly `Verdict: pass`. A red gate sends its findings to a fix agent in the same worktree, one fix round per item, and after it `tests` runs again and only the gates that were not green. A fix round or a review or audit session that fails or times out runs once more with the same instructions; when that try fails too, the chain ends: no further gate runs, and the pull request is a draft that says so. The details are in [the chain after the build](../concepts/verification-gates#the-chain-after-the-build).
8. **Opens one pull request** per item, against the base branch, only while the item carries `pulse:approved` and the `Plan-ok` its build began from, both from people who may push; otherwise the item fails and keeps its branch. Its body has `Closes #<n>`, a `| Gate | Result |` table, the commit the gates ran at, the RED note, the files outside the PLAN, and the review and audit reports. It is ready for review only when all three gates passed; otherwise it is a draft that names what is open. Right after, `pulse go` puts the review and audit verdicts on it as comments ([the pull request](../concepts/verification-gates#the-chain-after-the-build)). The item keeps its claim until the merge, so no later run builds it again. The slot stays busy until the pull request exists; then the run reads the board again and fills it.
9. **Repeats** until nothing is ready and nothing runs. Each item gets at most one planning job and one build per run, so nothing loops. In a terminal, a run with no agent at work stays on while an item waits at a gate a person opens: a PLAN at `plan waits for you` (gate 2), or a ready pull request the run holds (gate 3). It prints `go idle, waits for #n`, reads the board every 60 seconds, and a full read of an unchanged board at most every 5 minutes (GitHub answers the check in between with 304, which costs no rate limit). Once you approve, the run builds or merges. `q` ends it as a finished run, Ctrl-C as a stopped one; it also ends when nothing waits at gate 2 or 3 any more. An item waiting for its spec approval (gate 1) keeps no run on.

A build fails when its agent exits with an error, runs longer than `agent_timeout`, or leaves no change outside `_devprocess/` on the branch (`nothing built`: a PLAN, a needs file, or notes alone are none, and no pull request opens). A crash, a timeout, or a rejected push gets one more try in the run. An item that fails for good, a PLAN that still fails after its fix rounds, a worktree that cannot be set up, and a draft whose gates stay red after theirs get the label `pulse:failed` and a comment `pulse go: failed at <base>: <reason>`, and no run takes them again until a person runs `pulse approve <n>`. A failed item gives its claim back with that comment as its note (a draft keeps its claim), and its worktree stays for a look. One item's failure never stops the others.

Your merge ok is the last stop: `pulse approve <n>`, or `a` in the map, and the run merges the pull request ([Gate 3](#gate-3-the-merge)).

**Blockers.** A feature with an open blocker waits for the blocker's merge, even when the blocker's pull request is ready; nothing builds on a blocker's branch. The run closes items whose PR was merged into a base branch other than the repository's default, because GitHub closes issues on its own only for the default branch ("closed #n: its pull request was merged"). After the work round it removes clean managed worktrees of closed items; one with changes stays, and the run names it. Startup does not inspect all historical local branches before taking new work. A pull request that changes only files under `_devprocess/`, such as a spec, closes no item by its branch name; an item whose whole work lies there, you close on GitHub. While such a pull request is open, it is no pull request of that item either, and the run does not wait for its merge. A pull request from a fork counts for an item only through its `Closes #<n>`, since the fork's owner picks its branch name. GitHub links `Closes #<n>` only in a pull request into the default branch: a fork's pull request merged into another base branch closes nothing, and you close the item on GitHub. Nothing is built on a fork's branch.

## What the team sees while it runs

The board and origin carry the run's progress, so every clone's map shows it ([what the team sees, and when](../concepts/where-things-live#what-the-team-sees-and-when)).

- **Preparation before the first claim.** The local map shows the living runner while it loads the board, checks the current base, or sets up a worktree. `WHO IS DOING WHAT` names the activity, target, and elapsed time; `NEXT` explains what the runner does next or what the person must do. Preparation counts as runner activity, without adding an agent. It disappears when that process stops.
- **A sign of life per phase.** Each phase start (`plan`, `build`, `spec tests`, `tests`, `review`, `audit`, `fix`) puts the phase and the time on the item's claim mark, and a phase that runs long renews them every 10 minutes. A teammate's map shows `building, 4 min ago`; after 30 minutes without one, `no sign of life`. A mark that cannot be written costs a line in the item's log, never the item.
- **A push after every phase.** After an agent phase (plan, build, fix) that ended cleanly, `pulse go` commits what the agent left uncommitted (never `_devprocess/temp/`). Whenever a phase added commits, it pushes the item branch, a fast-forward only. Whoever holds the item next, in any clone, builds on that work. A rejected push stops the item: it fails and gives its claim back. A project hook that refuses a commit or push of `pulse go` pauses the run instead, see [the base check](#the-base-check). Before each push the run checks that it still holds the item. When another session's older claim holds it, or the run's own mark is gone, the item stops: nothing is pushed, no pull request opens, the work stays in the worktree, and the run takes its own claim back, so the item is its holder's alone.
- **A note on hand-back.** An item the run gives back after a failure or a stop keeps a note on the board: the phase, the reason, and the branch that carries the work pushed so far. A PLAN that still fails P1 to P6 after its fix rounds leaves one too. The map shows its first line as `last run: ...`, and `pulse status <n>` prints the whole note.

## One run per clone

A second `pulse go` in the same clone refuses to start while one runs (exit 2), so every agent of the clone belongs in one run. A run reads `.pulse/config.toml` once, at its start: a branch you check out while it runs changes neither its `verify` nor its base branch. It takes `setup`, `verify`, and `[agents]` from the base branch as origin has it, and refuses to start when `base_branch` in your working tree names another base than the file there. A run stopped with Ctrl-C, `kill`, or by closing the terminal stops its agents, gives the claims of the items still running back with a note, and prints the report so far; a second signal does not cut that short.

A run that ended without its cleanup (SIGKILL, a crash, the power) leaves its agents and claims. The next start in the same clone ends those agents, gives the claims of that run back to the ramp, and prints "took over #n from a stopped run"; the loop then claims them anew. An item with a pull request keeps its claim until the merge, and an item held for a person (below) keeps it too.

Runs of your login in other clones share the ramp through claims: the claims decide who builds what, and no run takes over an item another clone's run holds.

## The hold

After every phase, `pulse go` compares the whole git config the worktree reads, except `branch.*`, the shared `info/attributes`, the hooks, in the shared `hooks` folder and where `core.hooksPath` points for the worktree (husky: `.husky/_` in it), and the files that tie the worktree to the git directory with their state before the phase. An agent that can write there (Codex with `--add-dir`) could leave a program that later runs outside every sandbox and shows in no diff. When one of them changed, the item stops: nothing is pushed or thrown away, no further phase runs, and the claim stays, even across a hard stop of the run. Settings under `branch.*`, such as the merge base VS Code notes per branch, stop nothing; any other change to the config does, since `gpg.program`, `credential.helper`, or a remote's URL can run a program as you. When the change is one every worktree of the clone runs with (the git config, `info/attributes`, `.git/hooks`, commondir), the whole run halts: it launches nothing more and runs no git over the network, no fetch and no push, and items still in a phase stop the same way when it ends. The head says `the git setup of this clone changed at #n (...)`. The run compares with what it found at its start too, so a phase that began after a change still holds. The report, `pulse status`, and a note on the item name what changed. A draft whose gates run again gets the same text at the top of its pull request, starting with "Held by `pulse go`". Look at the named paths first. Then `pulse release --take <n>` frees an item without a pull request; a draft keeps its claim, and you take the hold note out of its text.

## Gate 3: the merge

A ready pull request of `pulse go` keeps its claim until it is merged, across runs: the claim names the run as `go:<clone>:<pid>`, and the next run in the same clone takes it over. You approve the merge with `pulse approve <n>`, or `a` in the map. It writes the comment `merge ok at <head>` and nothing else, and names the protected paths the pull request changes: `.pulse/`, `.github/`, `.husky/`, manifests and lockfiles, test-runner configs, the paths under `protected`, and those `setup` and `verify` name. A run merges only when all of these hold: a merge ok from someone who may push names the pull request's head, or a head that adds nothing to it but clean merges of the base; the tests gate passed on that head in this clone, and the review and the audit passed here on it or on a commit it builds on; the pull request is ready, GitHub can merge it, and its whole rollup passed. A status someone else set counts for nothing. When the base moved, the run merges the base in first, runs `setup` again after a lockfile changed, runs the tests gate at the new head, and pushes it; the next round merges that head. A conflict gets a fix round, after which the review and the audit run again, and the new head needs a new merge ok. The merge is bound to the head with `--match-head-commit`, in the repository's default merge method, never with `--admin` and never with `--auto`: GitHub keeps auto-merge after a push, so it could merge a head nobody approved. While checks still run, the pull request waits (`waits for GitHub checks`), and a later round or run merges it once they passed; an auto-merge an earlier version left on, the run turns off. Then the run closes the issue, and the epic with its last open item, also when the base is not the default branch. A pull request merged by someone else on GitHub closes at the start of the next run.

## Auto mode

With no explicit switch, gate 1 plan is on and gates 2 build and 3 merge are off. `pulse auto plan off` makes spec approval manual and records that choice even before a control issue exists. `pulse auto build on` delegates PLAN approval; `pulse auto merge on` delegates merging. An explicit off or expired delegation stays off. The display identifies the unset plan default as `plan auto`, without inventing a switch time. These choices apply to your own `pulse go` and your own items ([Commands](../reference/commands#pulse-auto)). The runner records the approval and its authority before applying the same checks as a personal approval:

- **Gate 1 plan**: for an item you opened whose spec passes R1 to R6, on the base branch or in its docs PR, the label `pulse:approved` and the comment `gate 1 approved by pulse go as @you (automatic planning)` for the default, or a comment naming your explicit switch. The comment names the docs PR's head and the spec path first when there is one. The run merges the docs PR and plans the item.
- **Gate 2 build**: with explicit build delegation, for a PLAN that passes P1 to P6, of an item you opened or whose claim the run holds, the `Plan-ok` line and the comment `plan ok at <plan blob> <spec blob>: gate 2 approved by pulse go as @you (auto build on since 10:12)`. The run then builds it. Without that delegation, the PLAN waits for your approval.
- **Gate 3 merge**: for a ready pull request the run holds, the comment `merge ok at <head>: gate 3 approved by pulse go as @you (auto merge on since 10:12)`, then the merge as in [Gate 3](#gate-3-the-merge).

Right before each of these the run reads the switches from GitHub, past every cache, so a switch you turned off a moment ago counts. It never pulls a lever from anyone else's switch, from one past its time, or while two open issues have the label `pulse:auto`; for an item with `pulse:hold`, `pulse:draft`, or `pulse:failed`; for an item you did not open (at gates 2 and 3, unless the run holds its claim); at gates 2 and 3 when the spec, the PLAN a Plan-ok approved, or the PLAN at the head has `risk:`, or the PLAN is gone from the head; and at gate 3 when the pull request changes a protected path, a manifest, or a lockfile (a moved file counts by its old name and its new one), when a gate's pass was carried over from an earlier head after a fix round instead of running at this head, when the head lacks the base the round checked (a merge of the base would carry the review and the audit over), without this clone's evidence for the head, or before its whole rollup passed. The report then names the item, `merge waits for a person: <reason>` (`plan` or `build` at the other gates), and the gate waits for your `pulse approve <n>`. A pull request that falls behind the base always waits for a person in auto mode: bringing the base in makes a new head whose review and audit are carried over, not run there. So of several items built in parallel, the first merges by itself and the others wait for your merge ok.

A pull request says `Merge: auto (@you, until 18:00)` or `Merge: waits for a person (<reason>)`. In a Herdr pane (`HERDR_ENV=1`), a gate of your item that waits for you sends `herdr notification show "Pulse: #<n> <gate> waits for you" --sound request` once per item, gate, and run; what herdr answers goes into the item's log, and a failure there stops nothing. `plan_approval` and `go_autostart` in `.pulse/config.toml` switch nothing: each command that reads the config says once `plan_approval is ignored: pulse auto build on switches gate 2 for your items`. That legacy hint names the explicit switch; an unconfigured build switch already follows spec approval.

## Given back with code

An approved item given back with `pulse release <n>` whose branch carries code goes straight into the gates at the next run: no agent builds it again. When it has a pull request already, such as a draft whose red gate you fixed, the run writes its text anew and marks it ready once all three gates pass. A draft you drop, you close on GitHub.

## The base check

The run fetches the current base SHA and reads the project's CI and existing evidence at that commit. It runs no full local test suite before planning or taking work. `setup` prepares an item's worktree; full verification belongs to the built result.

1. Current project CI failure or cancellation makes the base red, even when an older saved result was green. Its named check and available bounded diagnosis explain the next action.
2. Current project CI can replace a saved `pulse/base` verdict at this SHA. Without current CI, a saved failure remains binding unless GitHub proves its Dependabot cause was automatic maintenance, or this clone recorded the same SHA and failure text from an old local startup check. The report explains the reassessment; it creates no green status without passing CI or equivalent verification evidence.
3. Passing current CI or matching existing evidence lets work continue. A commit without CI also permits work, while the completed result must still pass the full tests gate.
4. Pending CI allows planning on the current commit; ordinary builds and merges wait for it. A red base permits only items labelled `pulse:base`, the repair items a person filed for it.

The run fetches the base itself for each check and starts items of that round from the SHA it evaluated. A failed fetch starts nothing. A stored status and local evidence remain readable, but startup launches no scratch worktree, dependency setup, or full verification of the base. The map, CLI, and report carry the same check, cause when known, and next action. If a Dependabot check explicitly names a missing secret, the action points to that repository's Dependabot secrets settings; unavailable details lead to the check itself.

GitHub's automatic Dependabot update search is excluded only when the GitHub Actions app, dynamic workflow path `dynamic/dependabot/dependabot-updates`, Dependabot actor, commit SHA, and check suite agree. A project check merely named `Dependabot` still counts. An API failure leaves the assessment unknown. This does not change Dependabot itself or require local registry credentials to be uploaded to GitHub.

Earlier versions ran base checks in temporary worktrees, which could fail because of machine prerequisites or tooling that denies paths under `.git`. Startup now creates no such checkout. Existing files and worktrees remain untouched. Item setup and the built result's tests gate still block failed work before integration, for both Claude Code and Codex.

**A hook that refuses.** When a project hook (`pre-commit`, `commit-msg`, `pre-push`) refuses a commit or push of `pulse go`, the run starts nothing new until the base moves or you start it again. The item gives its claim back with a note and does not fail, its worktree keeps the work, and the map head says `hook rejected: <hook> at #n`. `pulse go` never skips a hook.

## The report

The output names each start (`planning #n`, `building #n`, `merging the base into #n`, with the agent, branch, base, and worktree) and ends with the results:

- **planned**: each PLAN written in this run and its gate: `ready`, or `plan waits for you` with the reason.
- **done**: each finished item with its PR, the result of each gate, the fix rounds, and whether it waits for your merge or stays a draft. With it, the tokens, cost, and time its agents reported as JSON (the built-in templates do).
- **failed**: the reason (an exit code, timed out, nothing built, a push that failed, a claim lost to someone else, a branch that conflicts with its base, a PLAN that still fails a P rule, a hold, an approval gone while it was built, a GitHub error), the worktree, and the log `.git/pulse/go/<n>.log`, one section per phase.
- **limit**: an agent hit its usage limit in a phase, and until when. The item keeps its claim and its worktree and takes no slot; another agent of the run that may build it runs the same phase at once, else the run waits for the reset time the agent named (an hour when it named none, or a time more than 8 days off) and prints `#n resumes at <time>`, while the item's claim mark says `limit until <time>`. The agent gets no new item until then. Before the phase starts again the run reads the item: closed, no longer approved, on hold, or held by someone else, it starts nothing and says why. Without a terminal, a second limit after the reset gives the item back, so the run ends.
- **skipped**: an item someone else claimed first, an approval from someone who may not push, a docs PR it did not merge and why, a PLAN that fails a P rule and waits for a person, a held draft, a draft whose pull request targets another branch than the base, a crash that gets one more try, or a build that found work to come first and waits for its draft.
- **stopped**: an item that was in a phase when the run was stopped, or whose commit or push a project hook refused.
- **held**: why the run started nothing new: `base red: <check>`, `base not known yet: ...`, or `hook rejected: <hook> at #n`.
- **closed**, **took over**, and the kept worktrees of closed items, as above.

`.git/pulse/go/report.json` holds the same results. The run writes it after every event, so it keeps what finished even when the run is killed. `run` has the pid, the start, the end, and the signal that stopped the run; `items` has one entry per item with `result` (`planned`, `done`, `failed`, `limited`, `skipped`, `stopped`), `why`, `pr`, `log`, and `at`; `activity` names the current preparation with phase, target, start, detail, and next action, with an item or log when available; `base` holds the evaluated base state and bounded diagnostic details. `took`, `unclean`, and `halt` follow. Older reports without the extra fields remain readable. `pulse status` ends with one line on the last run and one line per failed item. Every agent phase also leaves a line in `.git/pulse/usage.jsonl`, to compare agents and models across runs.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | the run ended, or you pressed `q` while it waited, and nothing failed |
| `1` | an item failed, a PLAN fails P1 to P6 and waits for a person, the base is red or not known yet, a project hook refused a commit or push, or `pulse go` refused a nested runner or a start without a TTY |
| `2` | the run did not start, and the message says why: no `verify` on the base branch, a base branch that could not be fetched, a run already in this clone, an agent missing from `[agents]`, no installed agent to build or review with, or the board could not be read |
| `128` + signal | the run was stopped: `130` for Ctrl-C, `143` for SIGTERM, `129` for a closed terminal |

## Agents and permissions

The agent command is a template under `[agents]` in `.pulse/config.toml`; `{prompt}` becomes the instructions. Without an `[agents]` table these are the templates:

```toml
agent = "claude"
agent_timeout = 60        # minutes; a hung agent is stopped with its child processes

[agents]
claude = "claude -p --allowedTools {allow} --output-format json --permission-mode acceptEdits {prompt}"
codex = "codex exec --json --sandbox workspace-write --add-dir {gitdir} {prompt}"
```

A headless agent cannot answer a permission prompt, so it runs only what its template allows. `{allow}` lets Claude Code run `verify`, the `verify:` commands of the item's PLAN, and five git commands, and in the review and audit sessions `verify`, the five git commands, and four read-only forms on their checkout (`git -C tree diff`, `log`, `show`, `status`); `{gitdir}` lets Codex commit from its worktree. [Agent templates](../reference/configuration#agent-templates) says what each covers and how to fix a template copied from an older Pulse. A `verify:` command of the PLAN is allowed only when it starts with a program of `verify` or with a script of the repository, such as `bin/pulse check`; a shell or interpreter given code, a download, `npx`, `env`, or `sudo` never is, and the item log and the pull request name each command left out. An agent missing on `PATH` runs from the newest VS Code extension that bundles it. The review and audit sessions start from the agent that built the item. Pulse never bypasses an approval.

`pulse go` sets two limits itself, whatever your own settings allow, for the program a template runs (the name in `[agents]` does not matter): `codex` gets `-c sandbox_workspace_write.network_access=false` in every phase, so it reaches neither GitHub nor any server, and a template that could open its sandbox or its network, or names no workspace sandbox, stops the run before it claims anything ([Agent templates](../reference/configuration#agent-templates)); `claude` gets `--disallowedTools Bash(gh:*)`, and `{allow}` adds the runners of `[spec_tests]` that are no bare shell or interpreter to what it may run. No agent process gets a GitHub token or `gh` login. An item whose wave-1 spec test matches a pattern with `localhost = true` needs a server on localhost, which Codex cannot reach: no agent whose program is `codex` builds it, so Claude does (or an agent of your own), and when `agent` names only Codex it waits with `needs a Claude agent (localhost spec tests)`.

### Two agents at once

With two subscriptions, one run keeps both busy:

```toml
agent = "claude:2,codex:2"
```

A number caps that agent; a bare name gets `cap` slots, and `cap` counts every running agent of the run, planning, building, fixing, or checking. Each item goes to the agent with the most free slots, the first named on a tie; an item with localhost spec tests never goes to Codex. When an agent hits its usage limit, it gets no new item until its reset time, and the item it was working on goes on with another agent in the same worktree, or waits for that time with its claim.

## Without headless agents

The same ramp drives in-session subagents: `pulse status --json`, claim each row whose `stage` is `starts next`, start one subagent per item in its own worktree, and run `pulse status --json` again after each finishes. The session that started them claims, pushes, and opens the PRs; subagents never touch GitHub.
